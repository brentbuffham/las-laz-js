# Speed (0.3.0) Plan

**Goal:** LAZ decodes on every core; the hot loop does less; the demo decodes out of sight with a
progress bar, displays once, and recolours without re-reading.

**Agreed with Brent in chat, 2026-10-21:** *"The Laz and Las need to be quicker"* — the demo took
6.2 s on a 10 M-point LAZ, 76% of it in the arithmetic decoder core, on one of 24 cores; *"is
there a way to load in an offscreen and show a decoding progress bar and then display. also
colour changes and all force a re-read which seems a waste"* — *"Sure lets do that"*.

## Decisions

- **Parallel chunks.** LAZ chunks are independent. A pool of workers (browser `Worker`, Node
  `worker_threads`; cores − 1, at most 16) decodes the chunks of each window; the next window is
  started while the current one is decoded into columns. Output is byte-identical and in order.
  `openLas(src, { threads })`: default automatic, `1` = single-threaded (0.2.0 behaviour); falls
  back to single-threaded when workers cannot start. The pool lives for one scan and is closed
  in a `finally` (abort included), so no worker outlives a read.
- **Hot loop.** Same arithmetic, less overhead: powers of two from a table, Point10's 768 byte
  models created on first use, no closure per point in the layered items.
- **Demo.** Reads in the library worker with a progress bar, then builds the cloud once. Keeps
  Z, RGB, intensity and class; colour / ramp / range / point size recolour in place. Only the
  read filters re-read.

## Tests (oracles as before)

- threads 1 vs N: identical columns on every LAZ fixture, in windows smaller and larger than a
  chunk; PDAL hashes still match; a corrupt file still fails TRUNCATED with the file offset;
  abort stops and leaves no worker running; private samples (opt-in PDAL) still equal.
- Timings recorded before / after (Node and Chrome) in the ledger.
