## 1. Intent

Kirra draws up to 20–30 M points as one GPU geometry. A 160 M-point pit scan is ~2.5 GB on the
GPU and ~3.8 GB as Float64 xyz alone, past what a browser tab holds. 0.10.0 splits a LAS / LAZ
file into an octree of tiles kept in binary scratch (memory, OPFS through `ScratchBinaryFile`, or
a Node folder), picks the tiles a camera needs within a point budget, loads them as point
columns, edits them in place, and writes the edited cloud back to LAS / LAZ. The library
renders nothing: drawing, GPU buffers and the camera stay in Kirra.

Decisions (Brent, 2026-10-24):
- **Four consumers, one store, three releases.** The tile layout serves all four now:
  - **0.10.0:** build, store, reopen without rebuilding, 3D view selection by camera and budget,
    edits, write-out, demo;
  - **0.10.1:** the 2D top-set pyramid (highest point per XY cell at a few cell sizes, #129's
    comment), built from the store, rebuilt when the store's edit counter moves;
  - **0.10.2:** box / radius / nearest queries across tiles (snapping, picking), on the node boxes
    and the existing per-tile grid index.
- **Editable tiles:** delete / keep by selection, set a column (classify), add a column, transform
  (as a matrix on the store), write out LAS / LAZ. Tiles are the data, not a cache.
- **Storage:** a tile is the source's own LAS point records, optionally compressed as one LAZ
  chunk, plus a typed array per added column.
- **Build:** two streaming passes, memory bounded whatever the cloud's size (section 3).
- **Reopen:** a store survives a reload or a Kirra restart; it records the source's fingerprint
  as ecw-js's block cache does (name, size, date, a hash of the first 4 KB).

Success:
- The demo builds tiles from a private 28 M-point scan in a Worker, then flies around it within a
  point budget, edits it (delete a box, classify a polygon), and saves a LAS / LAZ that reads back
  with the edits; memory stays bounded throughout.
- A store reopened after a reload draws at once, without a rebuild.
- An unedited store written out gives back every source record byte for byte (in tile order).
- Nothing changes for a caller who does not use tiles.

## 2. Layout

**Octree, additive (Potree-style).** The root is a cube around the cloud. A node holds a
spread-out sample of its box; its eight children hold the rest. Every point is stored once, so
loading deeper nodes adds detail without repeating points, and a delete removes a point from the
one node that holds it: an area deleted entirely goes empty at every zoom, and nothing is
re-sampled. Node keys are `"D-X-Y-Z"` (depth and cell, as EPT / COPC name them).

**A store** is a folder of named binary blobs:
- `store-a.json` / `store-b.json`: the manifest, written alternately, each with a sequence number
  and a checksum; opening takes the valid one with the higher number, so a crash mid-write
  leaves the previous one.
  - It holds the layout version (1); the source fingerprint and point count; the header and VLR
    bytes; point format, record length, scale and offset; the LAZ VLR when compressed; the cube;
    each node's key, point count and tight box; the added columns (name, type, fill); the
    transform (4 × 4, identity at build); the edit counter and the delete counter.
- `<key>.<generation>.tile`: one file per node. An edit writes the node under the next
  generation, then the manifest, then removes the old file. Opening removes files no manifest
  refers to.
  - Contents: a 32-byte header (magic `LLZT`, layout version, flags, point count, records
    byte length, added-column count); the records (raw, or one LAZ chunk of the source's
    items); each added column as a little-endian typed array, in manifest order, 8-byte aligned.

**Where (`where`):** `{ memory: true }`, a Map of blobs (tests, small clouds; gone with the page);
`{ opfs: id }`, folder `las-tiles/<id>` through `ScratchBinaryFile` (`options.dir`; outside the
24 h scratch sweep); `{ dir: path }`, a Node folder. The three backends only get, put, list and
remove blobs; the store code above them is shared.

## 3. API

### Build and open

```js
var las = await openLas(file);
var store = await buildTiles(las, { where: { opfs: "scan-123" }, compress: true,
	tilePoints: 50000, chunkPoints: 2000000, threads, signal, onProgress, replace: false });
var store = await openTiles({ opfs: "scan-123" });      // after a reload: no rebuild
store.matches(file);                                     // true when built from this file
await listTiles();                                       // [{ id, points, bytes, source, built }] (OPFS)
await removeTiles({ opfs: "scan-123" });
```

The build, in a Worker in the browser (OPFS sync handles need one):
1. **Count pass:** stream the file decoding xyz only; count points in a 128³ grid over the cube
   (8 MB). A point outside the header bounds re-runs the pass on the true bounds.
2. **Chunks:** merge grid cells up the octree while a group holds ≤ `chunkPoints` points.
3. **Distribute pass:** stream again, decoding xyz only to find each point's chunk; append its raw
   record bytes to the chunk's scratch blob through small buffers.
4. **Chunk octrees** (independent, on the worker pool): split a node until it holds ≤ `tilePoints`;
   then bottom-up each parent keeps, per cell of a 128³ grid over its box, the point closest to
   the cell centre (ties: the lower record position), moved up from its children. Splitting
   stops at depth 20 or a node edge under 100 × the file's scale, so stacked duplicates make one
   larger leaf, not a runaway split.
5. **Upper levels:** the same sampling from the chunk roots up to the root.
6. **Compress** (`compress: true`): each node one LAZ chunk, on the pool.
7. **Manifest last.** Abort or error removes the partial store; a store with no manifest is an
   unfinished build, removed by `listTiles` / `openTiles`.

Memory: about `threads × chunkPoints × (record length + 24)` bytes (~120 MB a worker at the
defaults) plus the 8 MB grid, whatever the cloud's size. Progress: `onProgress({ phase: "count" |
"distribute" | "tiles" | "compress", done, total })`, each value once, climbing. The same file
and options give the same store, byte for byte, whatever `threads` is.

### View selection

```js
var pick = selectTiles(store, { viewProjection, width, height, pointBudget: 10e6, minPixels: 100, localOrigin });
// -> [{ key, depth, count, box }]: most important first; a node's ancestors always come before it
```

- `viewProjection`: 16 numbers, column-major, as Three.js `camera.projectionMatrix ×
  camera.matrixWorldInverse`, in world coordinates, or in coordinates minus `localOrigin` when
  given. Orthographic (Kirra's 3D camera) and perspective cameras both work: a node's size on
  screen is measured by projecting its eight box corners through the matrix, never from distance.
- A node outside the frustum (its box, moved by the store transform, tested against the six
  planes taken from the matrix) is skipped with its subtree. A box crossing the near plane counts
  as infinitely large.
- From the root, by a priority queue on screen size (ties by key): a node is taken while the
  running count stays within `pointBudget`; its children become candidates when it covers at
  least `minPixels` on screen. The root is always taken.
- Pure and synchronous on the manifest (`selectTiles(store.manifest, view)` works too), so it runs
  on the main thread every frame while tiles load in a Worker: ~5,000 nodes in under 2 ms.

### Loading

```js
var pts = await store.readTile(key, { fields: ["x", "y", "z", "rgb", "facet"], localOrigin, float32: true });
for await (var t of store.readTiles(keys, opts)) draw(t.key, t.points);   // LAZ tiles decode on the pool
```

The same `fields`, `localOrigin` and `float32` as `readPoints` (standard fields, `"extra"`, the
file's extra columns, added columns). Coordinates: record × scale + offset → the store transform
(Float64) → minus `localOrigin` → Float32 when asked. The library keeps no cache: the caller
holds what it draws and drops what `selectTiles` no longer returns.

### Edits

```js
var sel = await store.select(function (cols, tile) { return selectPolygon(cols, poly); }, { fields: ["x", "y"], box });
var sel = await store.selectBox(box);  /* selectPolygon(poly, opts), selectClasses(classes) */
var both = combineTileSelections(a, b, "union");   // "intersect" | "subtract"
await store.deletePoints(sel);         // or keepPoints(sel)
await store.setColumn(sel, "classification", 64);  // a value, or { [key]: typed array } per point
await store.addColumn("facet", "i32", -1);         // removeColumn(name)
store.transform(T);                    // composes with the store's matrix; no tile rewritten
```

- **A tile selection** is `{ counter, count, tiles: { [key]: Uint32Array } }`: sorted indices into
  each tile's points. `store.select` visits only the tiles whose box (moved by the transform)
  meets `box` when given, loads `fields`, and keeps what the callback returns (a `Uint32Array` or
  null). The helpers wrap the 0.5.0 selectors with the tile boxes as a first cut.
- **A selection made before a delete or keep is refused** (its `counter` no longer matches the
  store's delete counter): its indices would point at other points.
- **Delete / keep** rewrites each touched node compacted; a node left empty stays (its children
  still hold points). Counts, tight boxes (shrunk only; a stale box is still a safe bound) and
  both counters update.
- **Set a column** decodes the node's records, sets the column for the selected points and
  re-encodes the records through `encodeRecords`, so every other field stays byte for byte.
  Writable standard fields: `classification`, `intensity`, `userData`, `pointSourceId`, the
  `synthetic` / `keyPoint` / `withheld` / `overlap` flags, `rgb`; added columns. The writer's
  refusals hold (a class above 31 in point formats 0–5).
- **Add a column:** name and type as `layoutExtraBytes` takes them (scalar types 1–10; not a
  standard field, a file extra column or another added column), every point set to `fill`.
- **Transform:** `checkTransform` validates `T`. The node boxes keep the original frame; the
  matrix moves them for culling and selection. CRS is unchanged (as `transformPoints`).
- Edits run where the store's blobs are writable (a Worker for OPFS); one writer at a time
  (`BAD_STORE` naming the lock when another tab holds it).

### Write-out

```js
await store.writeLas(sink, { compress: true, chunkSize, threads });   // sink as createLasWriter's
```

Tile by tile through `createLasWriter`, never the whole cloud in memory: the source's version,
point format, scale and offset (re-chosen from the transformed bounds at the source's scale when
transformed), CRS, class names and extra bytes, plus the added columns as extra bytes. Points come
out in tile order; the original order is not kept. VLRs the writer does not write today are
dropped, as on any save.

### Worker

`createWorkerHandler` gains `buildTiles`, `openTiles`, `readTiles`, `selectTiles`, the edits and
`writeLas` (on a store), with the store's manifest posted back after each change so the main thread runs
`selectTiles` on its own copy.

## 4. Internals

`src/tiles/`: `store.js` (manifest, generations, the three backends), `build.js` (the two passes,
chunking), `octree.js` (chunk octree and sampling, pure on columns, run by the pool), `select.js`
(frustum, screen size, budget), `edit.js`, `write.js`. The build needs raw record bytes window
by window: `LasReader` gains an internal raw-window iterator beside `chunks` (the LAZ path
already makes these bytes before decoding them).

## 5. Demo

A **Tiles** tab: Build tiles from the open file (Worker, progress by phase, compress checkbox),
or reopen a stored one from a list (points, size, source); a budget slider (1–30 M) and a
"tiles drawn / points drawn" line; tiles load and unload as the camera moves. Edits on the
store: delete a drawn box, classify inside a polygon; Save writes the edited store (LAS / LAZ).
Remove a store. The existing tabs are unchanged.

## 6. Speed and memory

Targets on Brent's 28 M-point private scan (checked in the demo, not in CI): build within ~2× the
time of a full `readPoints`; reopen and first draw under 1 s; `selectTiles` under 2 ms a frame;
peak memory during the build within the section 3 bound. OPFS size about the source's record
bytes (raw) or about its LAZ size (compressed).

## 7. Errors

- `INVALID_ARGUMENT`: a bad option (named); a `where` that is not one of the three; building into
  an existing id without `replace`; a key not in the store; an unknown field; a selection from
  before a delete or keep; an added column name taken or reserved; `setColumn` on a field that
  cannot be set; a value the field cannot hold (as the writer words it).
- `UNSUPPORTED`: `compress` for point formats 4, 5, 9, 10; a store of a newer layout version.
- `BAD_STORE` (new): no valid manifest; a node file missing or failing its header check; the store
  locked by another tab or worker. The message names the store and the node.
- `ABORTED`: the build's `signal`; the partial store is removed first.

## 8. Testing (oracles, not snapshots)

- **Every point once:** after a build, the nodes' records, as a multiset, equal the source's
  records byte for byte; counts add to the header's; every point lies in its node's cube and in
  its tight box. LAS and LAZ sources, formats 0–3 and 6–8, extra bytes kept.
- **Sampling:** on a hand-built cloud, each parent holds exactly one point per occupied 128³
  cell, the point nearest the cell centre (computed in the test); leaves ≤ `tilePoints`; stacked
  duplicates stop at the depth limit.
- **Out-of-core:** a build with `chunkPoints` 1,000 on 50,000 points equals a build with one
  chunk, node for node; peak heap (the `test/helpers/peakMemory.mjs` harness) stays within the
  bound.
- **Determinism:** `threads` 1 and 4, compressed and not, give the same nodes.
- **Header bounds wrong:** a file whose header box is too small still builds, every point kept.
- **View selection:** against a brute force over all nodes: frustum culling (ortho and
  perspective matrices, a box across the near plane), the budget never exceeded, ancestors before
  descendants, larger on-screen nodes first; the result is the same from `store` and `manifest`.
- **Loading:** `readTile` columns equal `readPoints` of the same records (fields, extra columns,
  `localOrigin`, `float32`, the transform as `readPoints`' `transform`).
- **Edits:** delete / keep against the same selection applied to `readPoints` columns
  (`removePoints`); a stale selection refused; set column / classify against `classifyPoints`;
  other fields byte for byte; add / remove column; transform composes.
- **Write-out:** unedited → every source record byte for byte (in tile order); edited → equals
  `writeLas` of the same edits on in-memory columns, as multisets; LAS and LAZ; PDAL reads it
  (skipped without PDAL).
- **Reopen and crash safety:** reopen gives the same manifest; a manifest write cut short (fake
  backend that throws mid-write) leaves the previous manifest; orphan generations removed;
  `matches` true for the source, false for a changed file.
- **Backends:** the same store tests on memory, the fake OPFS (`test/helpers/fakeOpfs.js`) and a
  Node temp folder.
- **0.9.2 unchanged:** every existing test passes untouched.

## 9. Out of scope

- Rendering, GPU buffers, camera control (Kirra's).
- The 2D top-set pyramid (0.10.1) and cross-tile queries (0.10.2), beyond the layout serving them.
- COPC / EPT output; reading other tools' tile sets.
- Undo (a caller keeps its own; reverting is a rebuild).
- Building from a filtered read (classes, crop, thinning): build from the whole file.
- Keeping the source point order or a source-index column.
- Merging two stores; streaming a store to another machine.
