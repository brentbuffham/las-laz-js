# las-laz-js 0.4.0 — Write LAZ — Design Spec

- **Status:** design agreed in chat 2026-10-21; this spec awaits Brent's review
- **Author:** Brent Buffham (https://kirra-design.com), with Claude
- **Library spec:** `2026-10-21-las-laz-js-design.md`

## 1. Intent

Kirra's LAS export cannot write `.laz`. 0.4.0 adds LAZ (LASzip) **compression** to the
writers, for every point format the reader decompresses: LAS 1.2 formats **0–3** and LAS 1.4
formats **6–8**, with extra bytes. Files must open in any LAZ reader (PDAL / LAZperf, LAStools,
CloudCompare), not only in this library.

Decisions (Brent, 2026-10-21):
- Both families in 0.4.0: 0–3 (point-wise chunked, item version 2) and 6–8 (layered chunked,
  item version 3).
- **Vanilla JavaScript, zero dependencies, no WASM** — in the library and therefore in Kirra.
  The compressor is ported from laz-rs (Apache-2.0), as the decompressor was.
- PDAL is a **development-machine oracle only** (as since 0.2.0): never in `package.json`, the
  npm package, or Kirra.
- 0.4.0 is LAZ writing only. Selections and column operations are 0.5.0 (own spec).

## 2. Approach

Writing mirrors reading. Reading is *decompress a chunk into plain LAS records, then decode
them*; writing is *encode columns into plain LAS records (the existing `encodeRecords`), then
compress them chunk by chunk*. So every LAS writer option — version, point format, scale /
offset, `localOrigin`, CRS, software / system id / date — works for LAZ unchanged, and LAS and
LAZ output of the same points hold the same records.

Each item compressor lives in the same file as its decompressor (`Point10Compressor` beside
`Point10Decompressor` in `v2/point10.js`, and so on), sharing the models, tables and context
logic — as LASzip and laz-rs pair them — so the two sides cannot drift.

Rejected: compressing straight from columns (a second record-packing path that must stay
byte-identical to the first); laz-perf / LASzip as WASM (a dependency).

## 3. API

Same two functions, one new option:

```js
writeLas(points, { compress: true, ...lasOpts })        // → Uint8Array | Blob (.laz)
createLasWriter(sink, { compress: true, ...lasOpts })   // streaming, as today
```

- `compress` (default `false`): write LAZ.
- `chunkSize` (default `50000`, the LASzip standard; only with `compress`): points per chunk.
  Fixed-size chunks only (the VLR's chunk size field is that number, never variable).
- `threads` (only with `compress`; same meaning as `openLas`): compression workers; default
  automatic, `1` = this thread. Output is byte-identical whatever the thread count.
- `createLasWriter` with `compress` buffers records until a chunk is full, compresses it and
  writes it at its reserved position; `close()` compresses the final partial chunk, writes the
  chunk table after the last chunk, patches the 8-byte table offset at the start of the point
  data, and patches the header totals as it does now. Every supported sink is positioned, so the
  real offset is written (not LASzip's −1-plus-trailer form). `writePoints` batches of any size
  give the same bytes as one call.
- `compress` with point formats 4, 5, 9 or 10 (waveforms) → `UNSUPPORTED`, as on read.

## 4. File layout

As LASzip / LAZperf write it (matched to PDAL 2.10's fixtures):

- Header: point-format byte with bit 7 set (compressed); record length = the uncompressed
  record length; offset to point data includes the LASzip VLR.
- LASzip VLR, user id `laszip encoded`, record 22204: compressor, coder 0, LASzip version
  **3.4 r3**, options 0, chunk size, number of special EVLRs / offset (−1 / −1 as LASzip writes
  them), then the items:

| Formats | Compressor | Items (type / size / version) |
|---|---|---|
| 0 | 2 point-wise chunked | Point10 6/20/v2 |
| 1 | 2 | + GpsTime11 7/8/v2 |
| 2 | 2 | + RGB12 8/6/v2 |
| 3 | 2 | + GpsTime11 + RGB12 |
| 6 | 3 layered chunked | Point14 10/30/v3 |
| 7 | 3 | + RGB14 11/6/v3 |
| 8 | 3 | + RGBNIR14 12/8/v3 |
| extra bytes *n* | — | + Byte 0/n/v2 (0–3) or Byte14 14/n/v3 (6–8) |

- Point data: i64 chunk-table offset, the chunks, then the chunk table (version 0, chunk count,
  each chunk's byte count arithmetic-coded as integers predicted from the previous one — the
  inverse of `decodeChunkTable`).
- Point-wise chunk: first record raw, then one arithmetic stream for the rest.
- Layered chunk: first record raw, u32 point count, every field's layer sizes, then the layers
  (each field / layer its own arithmetic stream; an unchanged layer is written empty, as LASzip
  decides it).

## 6. Error handling

- Formats 4 / 5 / 9 / 10 with `compress` → `UNSUPPORTED` (waveform packets are not handled).
- `chunkSize` not a whole number ≥ 1 → `INVALID_ARGUMENT`.
- Existing writer refusals (bad version / format pair, EPSG-only CRS on 6–10, missing scale /
  offset for the streaming writer) apply unchanged.
- A worker failing mid-write rejects `writePoints` / `close` with the worker's error (as a
  failed decode does); a pool that cannot start means compression on this thread.

## 7. Testing (oracles, not snapshots)

1. **Byte-identical to LAZperf (primary).** For every fixture (f0, f1, f2, f3, f3x, f6, f7, f7x,
   f8): take the records PDAL itself decompresses (our reader's output, pinned to PDAL by the
   manifest SHA-256), compress them with the fixture's header and chunk size, and compare the
   point data (offset, chunks, chunk table) and the LASzip VLR with the PDAL file byte for byte.
   No PDAL needed at test time. A difference is investigated to its cause before anything is
   accepted; a difference that is a legitimate encoder choice is written into the test with
   its reason, and that fixture must still pass check 2.
2. **Other readers decode ours.** Opt-in (`LAS_PDAL=<path>`, as the samples test): PDAL
   decompresses each of our files to exactly the records written (SHA-256 per field), and
   `pdal info` reports no problems. Manual CloudCompare open before release.
3. **Round trip** through our reader, every format, `writeLas` and `createLasWriter`: 0 points,
   1 point, exactly one chunk, one chunk + 1, a custom `chunkSize`; many small `writePoints`
   batches give the same bytes as one.
4. **Real files** (private samples): a 10 M-point LAZ and the 1.2 GB cloud decode
   → compress → decode to the same records; size against the original and compression speed are
   reported.
5. **Parallel = single-threaded**: compressing on the pool gives byte-identical files.

Coverage thresholds unchanged. The function gate that already fails (browser-only worker code,
96.47 % against 97 %) is a separate fix, not part of this release.

## 8. Build order

Each step ends tested.

1. Promote the encoder and integer compressor into `src/laz/`.
2. Version-2 compressors, `compressChunk`, chunk-table encoder, LASzip VLR builder — byte-identical
   to f0, f1, f2, f3, f3x.
3. `writeLas` / `createLasWriter` take `compress` and `chunkSize` — round-trip and batch tests.
   (Kirra could already export format 0 as `.laz` here.)
4. Version-3 layered compressors — byte-identical to f6, f7, f7x, f8.
5. Pool compression (`threads`) — byte-identical to single-threaded.
6. Real-file checks, README (LAZ writing, credits), CHANGELOG, version 0.4.0.

After release, in the Kirra repo: `LASWriter` passes `compress: true` when the file name ends in
`.laz`.

## 9. Out of scope

Variable-size chunks; LASzip item version 4; waveform items; COPC; spatially sorted output;
anything from 0.5.0 onward.
